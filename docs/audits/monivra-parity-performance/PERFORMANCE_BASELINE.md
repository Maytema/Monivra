# Замеры скорости: две версии на одном эмуляторе

Эмулятор Android 14, Pixel 6 (1080×2400), x86_64, 4 ГБ, **программная графика** (swiftshader), анимации
включены. Release-сборки обеих версий, в каждую загружен один файл: 3000 операций за 18 месяцев. Одинаковые
касания (`input tap` / `input swipe`), кадры из `dumpsys gfxinfo <пакет> framestats`.

**Основной прогон — 8** (CI 43604723871, коммит аудита `9e91aba`; обе версии с данными: на
экране «3 102 124 KGS» и одинаковые остатки месяца). Прогон 7 — та же методика, только новое приложение
(старое в нём не загрузило данные); прогон 4 — первый, с менее точной методикой, для оценки разброса между
прогонами.

Числа — **время до успокоения, мс**: от начала движения (или от последнего броска, где так написано) до
последнего кадра перед первой паузой 250 мс. Медиана, в скобках — разброс повторов.

## Как читать

- Меньше — лучше. «Новое / старое» < 1 — новое быстрее.
- Абсолютные числа завышены программной графикой (кадр 35–150 мс против 8–16 мс на телефоне). Разброс между
  прогонами на одном коммите — до ~30 % (свайп периода в операциях: старое 0,69 с в прогоне 4 и 1,18 с в
  прогоне 8). Надёжны только различия в 2 раза и больше, повторившиеся в разных прогонах.
- «Кадров» у старого мало: WebView отдаёт системе не все свои кадры. Поэтому сравнивается время, а не число
  кадров.

## Внутренний замер нового приложения (сборка 76, тот же код 06360df)

`mobile/scripts/emulator-perf.sh` в сборке с `EXPO_PUBLIC_PERF=1` пишет паузы JS-потока
(`mobile-builds/builds/76/perf/perf-summary.txt`):

| Движение | JS занят всего | Самая длинная пауза JS | Кадров |
|---|---|---|---|
| Первое открытие «Операций» | 410 мс | 81 мс | 167 |
| 6 бросков списка операций вниз / вверх | 718 / 467 мс | 128 / 121 мс | 164 / 204 |
| Свайп периода ×3 назад / вперёд | 373 / 279 мс | 115 / 141 мс | 98 / 98 |
| Прокрутка статистики (3 вниз, 3 вверх) | 0 мс | 0 мс | 61 |
| Восстановление 3000 операций | 984 мс | 680 мс | 45 |
| Предпросмотр отчёта, первый раз | 1270 мс | 335 мс | 128 |

Значит, в медленных местах (первое открытие «Операций», прокрутка статистики) JS-поток **не** держит
приложение долго: время уходит на сами кадры — создание и отрисовку большого количества элементов (см.
`PERFORMANCE_ROOT_CAUSES.md`).
