# Причины медленной работы: что доказано и что пока гипотеза

Источники: замеры двух версий на одном эмуляторе (`PERFORMANCE_BASELINE.md`, прогоны `audit-results/runs/4` и
`runs/5`), скриншоты тех же прогонов, чтение кода. Каждая строка помечена:

- **ДОКАЗАНО** — есть замер или скриншот, и причина видна в коде;
- **ГИПОТЕЗА** — причина следует из кода, но профилировщиком (Perfetto / React DevTools Profiler) не подтверждена;
- **НЕ ПОДТВЕРЖДЕНО** — жалоба владельца, которую эмулятор не воспроизвёл (нужен телефон).

Важно для чтения: эмулятор рисует программно (`swiftshader`), поэтому каждый кадр у обеих версий 35–110 мс.
Сравнивать можно только версии между собой и только время «до успокоения» (settle) — счётчик «плохих кадров»
на программной графике почти всегда равен числу кадров и сам по себе ничего не говорит.

## R-1. Список валют (~200 строк): пустые строки при быстрой прокрутке

| | Старое приложение | Новое приложение |
|---|---|---|
| Как строится | все строки сразу одной HTML-строкой (`js/ui/currency-picker.js:94–96`, `codes.map(rowHtml).join("")`) | виртуальный список `FlatList` (`mobile/src/ui/currency-sheet.tsx:84–90`): сначала 14 строк, потом порциями по 16, окно 9 экранов |
| Пустые строки | невозможны: все строки уже в документе | возможны: при броске пальцем список обгоняет дорисовку порций |
| Высота строк | — | одинаковая (56 dp у строки, заголовок — фиксированный), но `getItemLayout` не задан: каждую строку список сначала рисует и меряет, и только потом знает, куда прокручивать |

Статус: **ДОКАЗАНО по коду** (механизм виртуального списка без `getItemLayout`), **по экрану — см. кадр в
середине броска** `rn/10-currency-list-mid-fling.png` прогона 5 (если на нём есть пустые полосы, это прямое
доказательство; если нет — эмулятор не успел их показать, и нужен кадр с телефона).

Почему старое не тормозит, хотя рисует всё: 200 строк HTML для WebView — это один проход вёрстки, который
делается один раз при открытии (замер «открытие списка»: старое ~0,1 с после касания, новое ~0,4 с).

Варианты исправления (не косметика, а устранение причины), по возрастанию затрат:
1. `getItemLayout` (строки фиксированной высоты) + `initialNumToRender` ≈ 2 экрана + `windowSize` 21 — список
   заранее знает позицию любой строки и держит больше дорисованного; дёшево, обратимо.
2. Обычный `ScrollView` со всеми строками, как в старом (200 × ~6 элементов): пустот не бывает в принципе, но
   открытие дороже; нужен замер открытия до/после на телефоне.
3. Библиотека с переиспользованием строк (FlashList) — новая зависимость, решение владельца.

Критерий готовности: на кадре в середине броска нет пустых строк (эмулятор и телефон), открытие списка не
дольше 0,4 с на эмуляторе.

## R-2. Свайп периода (операции, категории, статистика)

Замер (settle, мс; прогон 4, по 3 свайпа в каждую сторону): операции — старое 625–841, новое 664–867;
категории — старое 1374–1464, новое 537–597; статистика — старое 597–751, новое 527–641.

Статус: **НЕ ПОДТВЕРЖДЕНО на эмуляторе** — новое приложение не медленнее старого (на категориях в 2,4 раза
быстрее). Если на телефоне владельца свайп заметно хуже, причина в чём-то, чего эмулятор не показывает
(другая частота экрана, другой процессор, данные владельца). Нужна запись с телефона (`EXPO_PUBLIC_PERF=1`
сборка пишет паузы JS в системный журнал: `adb logcat -s ReactNativeJS`).

Что в коде делает свайп дороже, чем нужно (**ГИПОТЕЗА**, кандидаты для профилировщика):
- `mobile/src/ui/pager.tsx`: страницы ключуются по периоду; после свайпа соседняя страница становится текущей,
  а новая соседняя **монтируется целиком в том же коммите**, что и смена периода (`render(key, false)` для
  нового `next`/`prev`). Старое приложение рисует соседа лёгкой картинкой только во время жеста
  (`js/app/swipe.js`).
- Список операций текущей страницы получает `windowSize={current ? 9 : 1}` (`features/operations.tsx:294`):
  когда сосед становится текущим, его окно растёт с 1 до 9 экранов — дорисовка 4 экранов строк сразу после
  свайпа.

## R-3. Прокрутка списка операций (бросок пальцем)

Замер прогона 4: старое — первый кадр через 67 мс, успокоился через 3,0–3,4 с; новое — первый кадр через
2,2–3,0 с, успокоился через 5,5–6,3 с. Эти числа **под сомнением**: в прогоне 4 замер начинался сразу после
снятия дерева экрана (`uiautomator dump`), а оно включает службу специальных возможностей, которая
нагружает RN-приложение (каждое изменение экрана передаётся службе). В прогоне 5 перед каждым замером пауза
1 с и записано время каждого броска (`inputsMs`) — см. `PERFORMANCE_BASELINE.md`.

Что в коде нагружает прокрутку (**ГИПОТЕЗА**):
- `onScroll` с `scrollEventThrottle={32}` и `onViewableItemsChanged` (`features/operations.tsx:283–286`) —
  на каждое событие прокрутки JS обновляет «прилипающий» заголовок дня (`StickyDay`): работа на JS-потоке во
  время броска.
- Строки разной высоты (с комментарием выше) без `getItemLayout` — список меряет каждую новую строку.

## R-4. Прокрутка статистики

Прогон 4: старое — успокоилась за 0,31 с (18 кадров), новое — 1,62 с (64 кадра по ~100 мс). Каждый кадр
нового приложения на программной графике в 1,5 раза дороже: на странице SVG-диаграммы (кольцо, столбики с
сеткой оси, полосы категорий). **ГИПОТЕЗА**: перерисовка SVG при прокрутке (react-native-svg рисует на CPU в
программном режиме). На телефоне с GPU разница может исчезнуть — нужен замер на телефоне. Возможное
исправление, если подтвердится: `renderToHardwareTextureAndroid` / растеризация статичных диаграмм.

## R-5. Холодный запуск

Новое приложение запускается быстрее: первый кадр 1,2–1,5 с против 1,8–2,7 с, готово через 2,2–2,6 с против
4,3–4,9 с (старое ждёт запуска WebView). **ДОКАЗАНО** замером; причин тормозов здесь нет.

## R-6. Размер APK — не причина медленной работы

| | Старое | Новое (x86_64, эмулятор) |
|---|---|---|
| APK | 3,77 МБ | 31,9 МБ (arm64 для телефона: 31,2 МБ) |
| Код Java/Kotlin (`classes.dex`) | 7,1 МБ (сжато 2,5) | 7,3 МБ (сжато 3,2) |
| Нативные библиотеки | нет (движок — системный WebView) | ~22,4 МБ, хранятся **несжатыми** (так Android грузит их без распаковки — быстрее запуск): `libreactnative` 7,3, `libhermesvm` 2,8, `libexpo-sqlite` 1,8, `libexpo-modules-core` 1,5, `libappmodules` 1,5, `libc++_shared` 1,3, `rnscreens` 1,2, `rnsvg` 0,9, библиотеки картинок Fresco (`imagetranscoder`, `static-webp`, `gifimage`, `native-filters`) ~1,9 |
| Код интерфейса | HTML/JS/CSS ~0,5 МБ | `index.android.bundle` 3,4 МБ (байткод Hermes, несжатый) |

Размер почти целиком — движок React Native и библиотеки; на скорость работы экранов он не влияет (холодный
запуск нового быстрее). Уменьшить можно (BL-P3 в бэклоге): сборка AAB для магазина (телефон скачает только
свою архитектуру и сжатый вариант), отказ от неиспользуемых библиотек картинок, проверка, что R8 включён
(признак, что включён: сборка 5 упала из-за удалённого сжатием класса WorkManager — `mobile/app.config.ts:42`).

## Что нужно, чтобы превратить гипотезы в доказательства

1. Perfetto-трасса на телефоне владельца (или на эмуляторе с GPU) для трёх движений: бросок списка операций,
   свайп периода, бросок списка валют — видно, какой поток занят (JS / UI / RenderThread).
2. React DevTools Profiler в отладочной сборке — какие компоненты перерисовываются при свайпе.
3. A/B на одном эмуляторе: вариант R-1 (1) против текущего, одинаковые броски, кадры в середине броска.
