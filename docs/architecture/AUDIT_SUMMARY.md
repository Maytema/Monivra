# Итоги аудита и плана перехода на React Native

Дата: 11.11.2026. Ветка `docs/react-native-architecture` (от `android-first-apk`, коммит `298406b`).
Приложение, APK, идентификаторы, подписи и данные не менялись. Подробности — в остальных файлах этой
папки (на английском, для разработчиков и агентов).

Обозначения: **[Факт]** — проверено по коду или тестом в этом аудите; **[Рекомендация]**;
**[Допущение]** — нужно подтвердить пробным проектом (PoC); **[Вопрос]** — решение владельца.

## 1. Оценка текущей архитектуры

- [Факт] Около 19,5 тыс. строк JavaScript без фреймворка, 7,3 тыс. строк CSS, 5 Java-классов в оболочке
  Capacitor. Все данные — один JSON-документ в `localStorage` WebView (лимит около 5 млн символов: в нём же
  фото и до 10 внутренних резервных копий).
- [Факт] Балансы не хранятся, а каждый раз считаются из операций. Это главное достоинство: правка или
  удаление старой операции не может «сбить» баланс.
- [Факт] Тестов много и они полезные: 223 модульные проверки, 80 сценариев, 29 проверок Android-моста и
  ещё 23 в малых наборах. Все прошли 11.11.2026.
- [Факт] Заявленные слои на деле не соблюдаются: 98 из 133 модулей связаны одним циклом импортов. Часть
  денежных правил живёт в экранах (бюджеты, суммы на статистике и счетах). Денежная логика завязана на
  глобальный объект `appData`, поэтому её нельзя «просто переиспользовать»: её надо переносить на
  TypeScript, а старый код оставить эталоном для сравнения.

## 2. Самые серьёзные риски

1. [Факт, найден в аудите] **Сохранение несвязанной правки пересчитывает сумму в другой валюте по
   текущему курсу.** Пример: перевод 8 750 KGS → 100 USD; затем курс USD изменён; массовое добавление
   тега к этому переводу превращает 100 USD в 87,50 USD, и баланс долларового счёта падает. То же с
   переводом с комиссией при правке комментария. Не исправлял (запрет на изменение логики) —
   [Вопрос Q-F7].
2. [Факт] Пока приложение закрыто, плановые операции не проводятся. Напоминания неточные и не проверены
   после перезагрузки на реальном телефоне.
3. [Факт] Удаление счёта удаляет и его переводы, поэтому меняется баланс другого счёта. Удаление
   категории удаляет её операции. Защитная копия перед этим не делается — [Вопрос Q-F3].
4. [Факт] Для всех валют хранятся «сотые» (иена, вона, кувейтский динар — тоже с двумя знаками)
   — [Вопрос Q-F2].
5. [Факт] История пересчитывается по текущим курсам: правка курса меняет прошлые итоги, бюджеты и
   отчёты — [Вопрос Q-F1]. Комиссия расхода не видна ни в одной сумме расходов — [Вопрос Q-F4].
6. [Факт] React Native не может прочитать `localStorage` старого WebView. Перенос данных строится на
   файле данных (или на внутренней копии `files/mirror/data.json`).

## 3. Рекомендуемая архитектура [Рекомендация]

Модульное приложение с одним финансовым ядром:

- `domain` — чистый TypeScript: деньги, проводки, плановые платежи, бюджеты, отчёты, форматы файлов.
- `application` — сценарии-команды: каждая команда выполняется одной транзакцией.
- `data` — SQLite: схема, миграции, запросы, единственный «писатель».
- `platform` — уведомления, фон, защищённое хранилище, файлы.
- `features` — экраны.
- `ui` — дизайн-система с токенами, перенесёнными из текущего CSS.

Балансы по-прежнему вычисляются, но теперь одним SQL-представлением. Однократность плановых платежей
обеспечивает сама база: уникальный ключ «платёж + дата повторения». Вход, синхронизация и подписки — три
отдельных будущих модуля; схема к ним готова заранее (UUID, отметки времени, «надгробия» удалений).

## 4. Рекомендуемый стек [Рекомендация]

- **Основа:** Expo SDK 58 (React Native 0.88, React 19.3), сборки разработки (development builds), строгий
  TypeScript.
- **Навигация:** Expo Router.
- **Данные:** SQLite через `expo-sqlite` и Drizzle (миграции проверяются вручную). Состояние: база данных
  плюс небольшой Zustand для состояния интерфейса.
- **Уведомления и фон:** `expo-notifications`; `expo-background-task` либо собственный небольшой модуль
  WorkManager, если подтвердится требование сети.
- **Безопасность:** `expo-secure-store` и `expo-local-authentication`.
- **Языки:** i18next; английские ключи остаются, поэтому 1 302 русские строки переносятся скриптом.
- **Интерфейс:** свои компоненты на Reanimated и `react-native-svg`; графики свои.
- **Отчёты:** PDF через `expo-print`.
- **Тесты:** Jest, проверки на настоящей SQLite, Maestro на эмуляторе.
- **Сборка:** GitHub Actions, как сейчас.

[Факт по документации Expo] SDK 58 требует Android 7+, а нынешний APK работает с Android 6
— [Вопрос Q-P5].

## 5. Структура проекта [Рекомендация]

Новое приложение — в папке `mobile/` этого же репозитория, рядом со старым: старое служит эталоном
до приёмки. Внутри: `src/app` (только маршруты), `features`, `application`, `domain`, `data`,
`platform`, `services` (позже), `ui`, `i18n`, `test/parity`. Правила импортов проверяются в CI. Полное
дерево и примеры («новый тип счёта», «новый способ входа», «новый график»…) — в `PROJECT_STRUCTURE.md`.

## 7. Что можно переиспользовать

- **Правила:** перенос почти один в один, старый код служит эталоном — комиссии, калькулятор, курсы и
  округление, балансы, кредитные карты, долги, цели, периоды, фильтры, повторения и напоминания, бюджеты,
  модель отчёта, импорт CSV, план восстановления и слияния.
- **Данные:** таблица русских строк, список валют, пути иконок, цвета темы.
- **Тесты:** 223 проверки как спецификация, сценарии и фикстуры.
- **Формат файла данных:** новое приложение будет читать его всегда.

## 8. Что нужно переписать

- Все экраны и навигацию.
- Хранение: JSON в `localStorage` заменяется на SQLite.
- Отрисовку PDF: canvas и самописный PDF-писатель.
- Механизм перевода: сейчас регулярные выражения по HTML.
- Фото: станут файлами.
- Резервные копии: станут файлами.
- Слой платформы: уведомления, фон, PIN, биометрия, файлы.

## 9. Риски переноса данных

- Внутренняя копия может отставать от последнего сохранения до 0,8 с.
- PIN не переносится файлом данных, его нужно задать заново — [Вопрос Q-M3].
- Старые фиксированные комиссии хранятся дробными числами, перевод в целые проверяется.
- Импорт идёт одной транзакцией с проверками: количество записей, балансы каждого счёта по старому
  алгоритму, связи с плановыми платежами, обратный экспорт.
- При любой ошибке старые данные остаются нетронутыми.

Рекомендуемый путь — экспорт файла в старом приложении и импорт в новом, оба приложения стоят рядом
(откат — просто продолжать пользоваться старым) — [Вопрос Q-M1].

## 10. Android и iOS

- **Android.** Фон работает «по возможности»: WorkManager — не чаще раза в 15 минут и когда разрешит
  система. Экономия заряда и прошивки производителей могут задерживать. После «Остановить
  принудительно» ничего не запускается до открытия приложения. Точные будильники ограничены политикой
  Google Play.
- **iOS.** Фоновые задачи запускаются, когда решит система (часто ночью); надёжны только локальные
  напоминания и догоняющее проведение при открытии.
- **Общее.** React Native **не снимает** эти ограничения. Проведение «в ту же минуту при закрытом
  телефоне» невозможно без сервера, и даже тогда телефон узнает о нём после синхронизации.
